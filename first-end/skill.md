# first-end

## 做什么

给文件夹，做两件事：

1. **概念/实记内容** → 术语 + 大白话 + 记什么
2. **代码阅读** → PPT代码 → 知识点归属 → 结构分类 → 每行加注释

**不出题，只梳理。**

---

## 如果你是 0 基础 + 还有两天考试 + 第一次学就是期末

这种情况，正常学已经来不及了。你需要的是极限突击——只学会考的那部分，其他的先不管。给一个文件夹路径，剩下的交给它。

**注意**：这份文档是梳理，不是教材——它把你手上的PPT里会考的东西提炼出来。目标定位是**及格**，不是满分。概念表格覆盖选择题和判断题的核心，代码注释覆盖大题（写出运行结果、补全代码）的核心。偏题怪题不值得花时间去追。

---

## 代码阅读：一句话说清楚你要做什么

你唯一要做的事情，用用户的原话说就是：

> 基于PPT的代码 + 当前属于哪个知识点 = **第一次缩小范围**。
> 筛选出来的代码块，分析它是：
> - **函数（分散的）**：第一行在slide A、第二行在slide B、第十行在slide C，分开的，你需要跨页拼合；
> - **固定格式（闭环）**：连在一起的，if-else这样有头有尾有配套的，标记出来这是一个完整的闭合结构；
> - **单独块**：只有一行的，或者几行但每行各自独立、各管各的。
>
> 经过前两步筛选后代码已经很少了，所以**每一行都要加注释，一针见血**——说清楚这一行干什么、变量是什么、什么条件下走哪个分支。

这就是整个技能的核心逻辑。下面每一个小节都是对这句话的展开。

# 考试出题方式（一切围绕这四种）

你梳理代码时，唯一的目的就是帮用户应对以下四种考试题型。如果一个代码块不能对应到这四种题型中的任何一种，它就不该出现在输出里。

| 题型编号 | 题目形式 | 考什么 |
|:--:|:---|:---|
| ① | "请写出下面解析式的结果" | 列表/字典/集合解析式的运行结果 |
| ② | "执行以下程序，写出运行结果" | 完整程序逐行追踪，写出输出 |
| ③ | "写出下列代码运行结果" | 代码片段追踪，写出输出 |
| ④ | 给一半补另一半 | 给if补else、给try补except、给函数定义补调用等关联补全 |

# 代码阅读：三步过滤流程

这是 first-end 最核心的方法论。每一步都必须严格执行，不能跳过，不能简化。

```
PPT提取的全部代码
    ↓
第一步：按目录归属归类（这段代码属于哪个章节的哪个知识点？）
    ↓  去掉不属于任何知识点、纯粹是演示/装饰的代码
    ↓
第二步：分析代码结构类型（单独块？固定格式闭环？函数分散？）
    ↓
第三步：按类型输出（单独块→每行注释 / 闭环→整体+每行注释 / 分散→拼合+每行注释）
```

---

## 第一步：按目录归属归类

### 为什么要这样做

老师PPT里的代码不是随机出现的。每一段代码都在演示某一个具体的知识点——这个知识点在目录里有明确的位置。比如一段 `try/except` 代码，它属于"7.2 异常处理"节，而不是凭空飘着的。

**归属到知识点后会发生两件事**：
1. 你知道这段代码在讲什么——注释时能一语中的，不会瞎猜
2. 不属于任何知识点的代码（纯演示、装饰性代码、操作步骤截图）可以直接丢弃

### 具体操作

从PPT提取的文本中，每一段代码前后一定有标题或说明文字。用这些文字确定代码属于哪个知识点。

**例子**：
```
PPT Slide 8 标题："异常处理"
Slide 8 正文："通过try语句来定义代码块……通过except语句……通过finally语句……"
Slide 9 标题："内置的异常类"
Slide 10 正文：【例7.5】常见异常示例（1）
Slide 10 代码：>>> noname     # NameError
```

→ Slide 10 的代码属于"7.2 异常处理 → 常见内置异常类型"

### 哪些代码要丢弃

以下代码虽然出现在PPT中，但不对应任何"可考知识点"，**不要输出**：

- 纯操作步骤的截图/命令行（如 `pip install xxx`、`python -O xxx.py`）
- 仅用于展示IDE界面的代码（如"单击File→New File"）
- 案例研究中的完整项目代码（如"教务管理系统"几十个文件——不属于任何一个具体知识点）
- 思政案例中的代码
- 资源下载提示页、目录页中的零星代码片段
- PPT中只出现了一次、没有标题归属、没有解释说明的孤立代码行

**保留标准**：这段代码在PPT中有明确的标题归属 + 有文字说明在讲它 + 它能对应四种考试题型之一。三个条件全部满足才保留。

## 第二步：分析代码结构类型

确定代码属于哪个知识点后，分析这段代码的**结构**。代码分三种类型，每种的处理方式不同。

### 类型A：单独块

**特征**：
- 只有一行或少数几行
- 每行独立完成一个特定功能
- 行与行之间没有控制流关系（没有 if/for/while/try 等结构把它们串成一个整体）
- 每行各自演示不同的东西

**典型例子**：
```python
noname                 # 这一行演示NameError
int a                  # 这一行演示SyntaxError
1 / 0                  # 这一行演示ZeroDivisionError
```

**每一行都是一个独立的知识点**。它们恰好被PPT放在同一页，但彼此没有逻辑关联。

**处理方式**：每行拆开，各自写一行注释。如果行数较多，可以用表格列出"代码 | 异常类型"。

**判断口诀**：代码之间是"并列"关系（这行演示A，那行演示B），不是"先后"关系（第一行是第二行的前提）。

### 类型B：固定格式闭环

**特征**：
- 有一个**完整的控制结构**
- 开头和结尾是配套的：`try` 和 `except/finally`、`if` 和 `else`、`for` 和循环体、`def` 和函数体、`while` 和 `break`
- 代码块内部有严格的先后依赖关系（上一行的变量在下一行使用）
- 结构不能被拆散——拆开就没意义了

**典型例子**：
```python
try:                          # 开头
    f = open("testfile.txt", "w")
    f1 = open("testfile1.txt", "r")
except IOError:               # 配套的except
    print("没有找到文件或读取文件失败")
else:                         # 配套的else
    print("文件写入成功！")
finally:                      # 配套的finally
    f.close()                 # 结尾
```

```python
if score >= 60:               # 开头
    print("及格")              # if分支
else:                         # 配套的else
    print("不及格")            # else分支 → 闭环
```

**处理方式**：整体保留，每行加注释。注释要点明每行在整个结构中的角色（"try→尝试执行""except→捕获异常""finally→无论怎样都执行"）。

**判断口诀**：代码有一个"入口"和一个"出口"，中间被一个关键字结构（if/for/while/try/def/class/with）串成一个整体。拆开任意一行，整个结构就不完整了。

### 类型C：函数（分散）

**特征**：
- 一个完整的功能单元（通常是一个函数或类），但它的代码**散在PPT的多页slide中**
- 比如：类定义在slide A，类的方法在slide B，类的使用调用在slide C
- 或者：函数定义在一个slide，函数的调用测试在另一个slide
- 分开看每一页都不完整，合起来才是一个完整的功能

**典型例子**：
```
Slide 18：class NumberError(Exception):          ← 类定义（分散的第一部分）
              def __init__(self, data): ...
              def __str__(self): ...

Slide 18 下半部分：def total(data):              ← 使用函数（分散的第二部分）
              if i < 0: raise NumberError(str(i))

Slide 18 底部：data2 = (44, 78, 90, -80, 55)    ← 测试调用（分散的第三部分）
              print('总计=', total(data2))
```

**处理方式**：
1. 先找到这个函数/类的所有部分（跨slide搜索同名函数/类）
2. 拼合成一个完整的代码块
3. 分三段输出：**类/函数定义** → **使用函数** → **调用测试**
4. 每段各自每行加注释

**判断口诀**：你在当前slide看到一段代码引用了某个函数/类，但这个函数/类的定义在前面或后面的slide里 → 它就是分散的，需要你跨页拼合。

**不需要拼合的情况**：如果函数定义和调用在同一个slide内的同一个代码块中（连在一起），就不算分散，按固定格式闭环处理。

### 自定义异常类 NumberError

**类定义**：
```python
class NumberError(Exception):                                          # 继承Exception，自定义异常
    def __init__(self, data):                                          # data=触发异常的数据
        Exception.__init__(self, data)                                 # 调用父类构造
        self.data = data                                               # 保存数据
    def __str__(self):                                                 # print异常对象时调用
        return self.data + ': 非法数值(< 0)'                            # 输出格式
```

**使用函数**：
```python
def total(data):                                                       # 对序列求和，遇负数抛异常
    total = 0                                                          # 累加器
    for i in data:                                                     # 逐个取值
        if i < 0: raise NumberError(str(i))                           # 负数→抛自定义异常
        total += i                                                     # 非负数才累加
    return total                                                       # 全部非负数才走到这
```

**测试调用**：
```python

```

# 概念/实记内容

## 什么情况走概念路线

一段PPT内容如果满足以下条件，走概念路线，不走代码路线：
- 主要是定义、分类、特性、原则的文字描述
- 没有可执行的代码块
- 或者有代码但代码仅作为概念的附属示例（不是为了让你读代码，是为了让你理解概念）

## 输出格式

```markdown
## 7.1 程序的错误（目录节标题）

| 术语/概念 | 大白话 | 记什么 |
|:---|:---|:---|
| 语法错误 | 代码拼写语法问题，编译都过不了 | 又称编译错误；判断：if后没冒号→SyntaxError |
| 运行时错误 | 语法对但执行时炸了 | 选择：NameError/ZeroDivisionError/FileNotFoundError的触发条件 |
| 逻辑错误 | 能跑不报错但结果不对 | 判断："程序不报错=结果正确"→ ❌ |
```

- "大白话"列：用人话，不用术语解释术语。方法：①去掉专业词→②换成日常场景→③检查"奶奶能听懂吗"
- "记什么"列：考试最可能怎么考这个点——填空关键词、选择的易混项、简答的要点条数、判断的关键对错点

# 犯过的错误（绝对不能犯）

以下错误是在真实对话中犯过的，每一个都导致了用户的不满。必须刻在脑子里。

## 错误1：删除PPT里有的内容

**表现**：更新版本时把"7.1 程序的错误"整节删掉了，因为觉得它不是代码。

**为什么错**：PPT里有，用户要你梳理，你就不能删。判断"这个不考"是AI替用户做的决定——用户没让你做这个决定。

**正确做法**：PPT里有的，都保留。概念归概念路线，代码归代码路线。只有明确属于以下情况的才删除：资源下载提示、二维码、思政案例、案例研究的完整项目代码（这些在"第一步"中已经定义了删除标准）。

## 错误2：加入PPT里没有的自己的知识

**表现**：在解释"为什么不是数值不能为负"时，补充了"异常捕获顺序"的推理和"基类放最后"的规则——这些PPT里确实有（在例7.10的标题和正文中明确写了），但"为什么不是数值不能为负"这句自己的推理，超出了PPT内容。

**正确做法**：注释只写PPT里有的信息。如果PPT明确说了"两者的顺序应该交换""Exception是所有派生类的父类"，注释可以写这些。如果PPT没有解释原因，就不补充。

**判断标准**：写完每行注释后问自己——"这句话是从PPT原文来的，还是我自己推理出来的？" 如果是从PPT来的，留。如果是自己的推理，删。

## 错误3：因为内容多就简化

**表现**：用户明确说"如果给你的ppt、文档等内容过多，你要仔细阅读，不能因为上传的东西多就简化、偷懒"。

**正确做法**：
- 有多少个知识点，就输出多少个。20个知识点不嫌多，2个知识点不嫌少
- 每个代码块都必须逐行加注释，不能因为代码多就只注关键行
- PPT有多少slide，就逐slide看多少slide。不能取样、不能只读前几页
- 提取文本62万字？那就全部读完再输出。不准跳

## 错误4：把不考的代码也输出来

**表现**：最初版本的代码部分输出了大量完整代码示例，包括logging的分步配置、案例研究的倒计时程序等——这些不对应四种考试题型。

**正确做法**：每个代码块输出前，做最后一轮检查——"这段代码能出成①解析式结果②③写出运行结果④补全代码中的哪一种？"如果四种都不匹配，不输出。如果代码块只匹配概念（如"这是logging的配置步骤"），它应该走概念路线，用术语表格输出，而不是用代码块输出。

## 错误5：输出路径不完整

**表现**：最后告知用户文件位置时，只给了 `Ch07_xxx.md` 这样的相对路径，用户不知道文件在哪。

**正确做法**：每次梳理完成，**必须输出完整绝对路径**，格式如下：

```
- Markdown：D:\develop\ai\Ch07_错误和异常处理_梳理_first-end.md
- HTML：D:\develop\ai\Ch07_错误和异常处理_梳理_first-end.html
```

不能只写 `Ch07_xxx.html`，不能只写 `.\Ch07_xxx.html`。盘符、目录、文件名一个不能少。

## 错误6：代码注释太笼统

**表现**：只给"作用"和"格式"的概括，没有逐行注释。

**正确做法**：经过三步过滤后剩下来的代码已经很少了。**每一行**都要写注释，一针见血——说清楚这一行在干什么、变量是什么、什么条件下走哪个分支、什么时候会出错。不要写"该函数用于求和"这种笼统的，要写"total=0 初始化累加器""if i<0: raise 遇到负数立刻终止循环""total+=i 非负数才累加"。

# 核心代码加粗规则

## 一、为什么要加粗

梳理完代码后，每个代码块 10 多行，但真正和知识点挂钩的核心结构只有 5 行左右。加粗的目的：**让眼睛一秒定位固定骨架**，和会变的东西区分开。

## 二、核心怎么判断

**核心 = 和知识点名称直接挂钩**。一段代码属于哪个知识点，那个知识点名字里有什么，什么就是核心。

| 知识点名 | 核心 |
|:---|:---|
| 引发异常 — raise | `raise` 那一行 |
| try…except…else…finally | `try:` `except:` `else:` `finally:` 那四行结构头 |
| 捕获异常的顺序 | `except Exception:` `except ValueError:` 那两行 |
| finally块 | `finally:` `break` 行 |
| 自定义异常类 | `class` 定义行 + `__init__` `__str__` 方法行 + `raise` 使用行 |
| assert语句 | `assert` 那一行 |
| print跟踪法 | `print(` 调试输出那一行 |
| 默认配置 | `logging.debug/info/warning/error/critical()` 调用行 |
| basicConfig控制台 | `logging.basicConfig()` 那一行 |
| 输入整数验证 | `def` `try:` `except:` `else:` `break` `return` 结构行 |
| 文件异常处理 | `try:` `with` `except:` `else:` `break` 结构行 |

**支撑行不标**：变量赋值（`a=1` `total=0`）、print 输出（当它不是知识点核心时）、文件操作（`f.write()`）、用户输入（`input()`）——这些是"肉"，不是"骨架"。

## 三、同一个词在不同知识点里角色不同

`print` 在"print跟踪法"知识点里是核心（加粗），在其他代码块里只是普通输出语句（不加粗）。`except` 只在异常处理相关知识点里加粗。**一切都由知识点决定，不是全局规则。**

## 四、核心行上只标"固定不变的东西"，会变的不要标

### 固定不变的（加粗下划线）

| 类别 | 示例 | 说明 |
|:---|:---|:---|
| 控制流关键字 | `if` `else` `for` `while` `try` `except` `finally` `def` `class` `return` `raise` `break` `with` `assert` | Python 语法保留字，永远这样写 |
| 内置函数/类名 | `print` `open` `input` `str` `int` `range` | Python 自带，名字不会变 |
| 异常类名 | `Exception` `ValueError` `IOError` `FileNotFoundError` `KeyboardInterrupt` `NumberError` | 异常类型名字是固定的 |
| 格式符号 | `:` `(` `)` `;` `"` `'` | 语法分隔符，Python 规定死的 |

### 会变的（保持原样，不加粗）

| 类别 | 示例 | 说明 |
|:---|:---|:---|
| 运算符 | `<` `!=` `+` `-` `/` `*` `==` `>=` | 题目决定用哪个运算符，外界决定 |
| 变量名 | `a` `b` `total` `result` `data` | 用户自己命名，可以叫任何名字 |
| 数字 | `0` `1` `10` `-80` `44` | 题目给什么就是什么 |
| 字符串内容 | `"数值不能为负数"` `'除数不能为0'` | 报错文字随场景变化 |
| 注释 | `# 这是注释` | 人写的说明，不固定 |

### 实例

```
if a < 0: raise ValueError("数值不能为负数")
```

| 部分 | 角色 | 是否加粗 |
|:---|:---|:---|
| `if` `raise` `ValueError` | Python 语法骨架，永远这样写 | ✅ 加粗下划线 |
| `:` `(` `)` | 格式符号，Python 规定死的 | ✅ 加粗下划线 |
| `a` `0` | 变量名、数字，别人可以叫别的 | ❌ 保持原样 |
| `<` | 运算符，题目决定用哪个 | ❌ 保持原样 |
| `"数值不能为负数"` | 报错文字，可以随便写 | ❌ 保持原样 |

```
assert b != 0, '除数不能为0'
```

| 部分 | 角色 | 是否加粗 |
|:---|:---|:---|
| `assert` | 关键字 | ✅ 加粗下划线 |
| `b` `0` | 变量名、数字 | ❌ 保持原样 |
| `!=` | 运算符，题目决定 | ❌ 保持原样 |
| `'除数不能为0'` | 字符串内容 | ❌ 保持原样 |

## 五、处理流程（完整链路）

```
PPT 全量代码
  ↓ 三步过滤（归属知识点 → 分析结构类型 → 筛掉不可考代码）
  ↓ 得到：缩小后的代码块，每个代码块属于一个具体的知识点
  ↓
定位到该知识点 → 确定核心结构是什么
  ↓ （验证：核心结构必须来自 PPT，不能自己编造）
  ↓
核心行检测：逐行匹配，找出和知识点挂钩的那些行
  ↓
核心行内：只标固定语法骨架（关键字 + 格式符号 + 内置函数/异常类名）
           不标会变的部分（运算符 + 字符串 + 变量名 + 数字 + 注释）
  ↓
非核心行：完全不动
```

## 六、技术实现

markdown 写完后，用 pandoc 生成 HTML，再跑 `highlight_core.py` 后处理脚本。脚本逻辑：

1. 解析 HTML，找到每个 `<h3>` 知识点标题
2. 根据知识点名匹配核心行正则模式（见第二节表格）
3. 在每个核心行内，找到 pandoc 生成的 `<span class="XX">` 标签
4. `cf` `kw` `pp` `bu` `im` 类 span → 包 `<b><u>`（固定骨架）
5. `st` `va` `dv` `co` 类 span → 不包（会变的东西）
6. `op` 类 span（运算符）→ 不包（题目决定）
7. 裸文本中的 `:` `(` `)` → 包 `<b><u>`（格式符号）
8. 裸文本中的 `logging.debug` 等方法名 → 包 `<b><u>`

```bash
# 完整生成命令
python <SKILL_ROOT>/scripts/extract_text.py --dir "<文件夹路径>"
# 写 .md 文件
pandoc input.md -o output.html --standalone --embed-resources --metadata title="标题" -H <SKILL_ROOT>/scripts/style-fix.html
python <SKILL_ROOT>/scripts/highlight_core.py output.html
```

# 内容量处理铁律

当你面对大量PPT/文档时，以下规则不可违反：

1. **必须逐slide阅读提取文本**。不能用"前几页就能代表后面"的假设。老师可能把最重要的知识点放在最后一章的最后几页。
2. **必须逐节梳理**。目录里有10节，你就梳理10节。不能因为"后面几节不太重要"就跳过或合并。
3. **每个代码块都必须逐行注释**。代码筛完后已经很少了，不能因为"这些代码都很简单"就不写注释。用户就是要看注释。
4. **不能取样、不能跳读、不能"后面类似的不写了"**。即使第5章和第6章结构相同，也必须各自完整梳理。
5. **如果提取的文本太长（超过上下文窗口）**，分批处理。每批5章，每批都按完全相同的标准和深度输出。不能第一批详细、后面几批简略。

## 输出格式

最终输出为 **HTML 文件**，双击即可在浏览器中打开。生成方式：

1. 先按上述规则写出 `.md` 文件
2. 用 pandoc 转换为自包含 HTML（`--standalone --embed-resources`）

```bash
pandoc input.md -o output.html --standalone --embed-resources --metadata title="课程名·期末梳理"
```

HTML 文件特征：
- 一个文件包含所有CSS/字体/资源，拷到任何电脑上双击都能打开
- 表格、代码块、标题层级完整保留
- 浏览器打开后可以 Ctrl+P 打印为 PDF

**输出完成后必须做的事**：告知用户完整绝对路径，格式如下（盘符、目录、文件名一个不能少）：

```
- Markdown：D:\develop\ai\xxx_梳理_first-end.md
- HTML：D:\develop\ai\xxx_梳理_first-end.html
```

**禁止**只写相对路径（如 `Ch07_xxx.html`）、禁止只写文件名、禁止用 `.\` 代替目录。
